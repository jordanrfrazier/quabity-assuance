# Direct agentic QA competitors

Checked: 2026-09-09. Read-only public documentation, vendor sites, and vendor-owned repositories. No accounts, demos, installations, target runs, or provider calls. Documented behavior below is vendor-described, not independently benchmarked. Public pages are mutable and several fetches failed; confidence concerns documentation support, not reliability in practice.

## Findings that change the competitive framing

- Ranger means **Ranger Feature Review at ranger.net**, with `@ranger-testing/ranger-cli` and docs.ranger.net. It is not Apache Ranger, the terminal file manager, RAGNER API orchestration, or CMU's cyber-range Ranger. The [official quickstart](https://docs.ranger.net/getting-started/quickstart/) identifies the package and even documents the file-manager command collision.
- Local agentic browser verification with reviewable evidence is already a direct competitive workflow. Ranger documents it explicitly. Its verifier is a separate Claude SDK instance, so describing it as the coding agent evaluating in its own context would be wrong. [Architecture](https://docs.ranger.net/concepts/how-it-works/).
- BLOCKED is not unique: Ranger has blocked and partial verdicts; Momentic Mo has blocked cases and explicit coverage gaps. Qabot should compete on what each verdict proves and how its approval/version/evidence chain behaves, not on the label. [Ranger architecture](https://docs.ranger.net/concepts/how-it-works/), [Mo reports](https://momentic.ai/docs/mo/reports).
- Independent execution context is not an independently sourced requirements oracle. Ranger scenarios are generally authored by the coding agent and can be reviewed in planning. Its public docs do not settle whether scenarios are bound immutably to a human-approved requirements version. That is unresolved, not an established absence. [Scenarios](https://docs.ranger.net/concepts/scenarios).

## Ranger Feature Review

**Documented workflow.** Setup authenticates the CLI and installs Chromium; an app profile supplies URL and saved login state. Coding-agent integration creates scenarios and invokes `ranger go`. The verifier runs locally; screenshots, video, traces and conversation logs go to the Ranger API/dashboard. Reviews support comments, approval/change requests, PR-summary generation and promotion of verified scenarios into persistent E2E tests. The surrounding coding agent can fix and rerun. These are product docs, not measured outcomes. [Quickstart](https://docs.ranger.net/getting-started/quickstart/), [architecture](https://docs.ranger.net/concepts/how-it-works/).

**Concrete ideas to borrow.**

1. Make each journey its own review unit: stable name, expected result, verdict, evidence links, and a human disposition. For qabot's offline ZIP, the entry page can give the reviewer this same short route from behavior to evidence without a service dependency.
2. Separate reusable access profiles from behavior specifications. Ranger distinguishes where/how to access an app from what to verify; its scenarios explicitly do not share browser sessions. Qabot can make fixture and authentication prerequisites reviewable without embedding credentials in journey prose. [Profiles introduction in quickstart](https://docs.ranger.net/getting-started/quickstart/), [scenario isolation](https://docs.ranger.net/concepts/scenarios).
3. Offer deliberate promotion of a reviewed journey into a reusable local regression case. Preserve the original evidence and approved plan hash; promotion should not retroactively change the result being reviewed. This is an adaptation of Ranger's documented scenario-to-test path, not a claim that Ranger implements this hash policy.

**Risk / anti-pattern.** Ranger's docs say profiles are organization-shared by default; qabot's default should fit its local evidence boundary. Its autonomous fix/reverify loop is a different scope from qabot's reviewer role. Scenario independence in separate browsers does not prevent backend data collisions; Ranger itself advises serial execution when scenarios interfere. [Quickstart](https://docs.ranger.net/getting-started/quickstart/), [scenarios](https://docs.ranger.net/concepts/scenarios).

**Confidence / unresolved.** High confidence in documented CLI/local-browser/evidence workflow. No hands-on validation of isolation, verdict correctness or evidence completeness. Human-approved immutable oracle/version binding and offline export behavior were not established by the reviewed docs. No verified exact public price recorded.

## Momentic, Including Mo

**Documented workflow.** The main Momentic suite has a repository CLI for authoring, local/CI execution, linting and reports. Its current documentation index also lists migration away from cloud authoring toward repo-owned tests. Mo is a separate private-beta QA agent: provide a running target and brief; it plans cases, explores and runs them, then uses a fresh reproducer for suspected bugs. The reproducer inherits neither browser state nor fixtures from discovery. Web execution is hosted, with a tunnel option for local builds. [CLI overview](https://momentic.ai/docs/cli-reference/momentic/overview), [current documentation index](https://momentic.ai/docs/llms.txt), [Mo](https://momentic.ai/docs/mo).

**Concrete ideas to borrow.**

1. Add a bounded fresh-context reproduction pass for high-confidence product defects. Preserve initial observation separately, and attach a second execution's reproduction evidence rather than treating a judge's agreement as reproduction. Mo's design is a stronger product idea than merely adding more model votes. [Mo agent roles](https://momentic.ai/docs/mo).
2. Put unmet prerequisites and unverified acceptance criteria beside every verdict. Mo records preconditions, outline, acceptance criteria, verified portions, gaps, and control-level checked/failed/partial/out-of-scope status. Qabot's report should make an omitted or inaccessible criterion impossible to confuse with a pass. [Session reports](https://momentic.ai/docs/mo/reports).
3. Distinguish interaction recovery from changes to the test contract. Momentic documents locator repair, temporary obstacle recovery, permanent healing and quarantine as separate layers; temporary recovery is bounded and recorded. For qabot, a cookie-banner dismissal would need to be an explicitly reviewed step or proposed plan change. Its current contract forbids silent retries and fallback; this is not a recommendation to enable recovery implicitly. [AI test maintenance](https://momentic.ai/docs/reliability/auto-maintenance).

**Risk / anti-pattern.** Mo says unreproduced suspicions never reach the bug report. Qabot should retain these as inconclusive observations so intermittent evidence is not discarded, while withholding a confirmed-defect claim. Momentic's maintenance configuration can route heal/warn results to successful CI exit codes; qabot should keep run truth separate from any downstream release policy. These recommendations are qabot-specific judgments. [Mo](https://momentic.ai/docs/mo), [maintenance and CI routing](https://momentic.ai/docs/reliability/auto-maintenance).

**Confidence / unresolved.** High confidence in the documented product distinction, report structure and private-beta status; no availability or quality validation. Some `.md`/brief URLs failed to fetch; use the successfully opened HTML pages above. The docs explicitly list Mo pulling a repo and doing its own setup/teardown as unavailable yet; this is a vendor-stated limitation, not an inference from silence. Public exact pricing was not verified.

## Bug0 and Passmark

**Documented workflow.** Bug0's current front page emphasizes managed QA: a forward-deployed engineer maps critical flows, builds tests, verifies failures, files reproducible reports and handles release gating. Passmark is its public Playwright library, accepting natural-language steps and assertions within real tests. Its README documents multi-model assertions, an arbiter or fail-on-disagreement policy, opt-in video assertions, caching and visual computer-use mode. [Bug0](https://bug0.com/), [managed QA](https://bug0.com/p/managed-qa), [Passmark repository](https://github.com/bug0inc/passmark).

**Concrete ideas to borrow.**

1. Include both sides of evaluator disagreement in evidence. Passmark documents a fail-on-disagreement mode with both models' reasoning. For qabot, record disagreement as evidence uncertainty and require grounded adjudication; do not claim that consensus establishes truth.
2. Let a criterion name its evidence modality. A transient toast, animation or temporal order may require video, not the final screenshot. Passmark's video assertion support is a concrete precedent. This need not entail a provider upload by default: qabot can retain local footage and explicitly indicate whether temporal evidence was actually assessed.
3. Turn coverage planning into a reviewable deliverable. Bug0's managed process starts with an agreed critical-flow list, not merely execution volume. Qabot's proposed journey list can distinguish accepted, deferred and blocked coverage, linking each to repository/docs evidence. [Managed planning](https://bug0.com/p/managed-qa).

**Risk / anti-pattern.** Additional judges introduce latency/cost and can share correlated mistakes. Passmark explicitly skips coordinate caching in computer-use mode because viewport changes make actions nonportable. Qabot's current actor/judge reads text and accessibility evidence, not screenshot pixels. If a future coordinate/visual mode is considered, do not transfer ARIA-based caching assumptions into it. Bug0's managed-service guarantees rely on a human service layer; they are not evidence of fully autonomous QA reliability. [Passmark](https://github.com/bug0inc/passmark), [managed QA](https://bug0.com/p/managed-qa).

**Pricing, checked 2026-09-09.** Bug0's homepage lists $2,500/month for the dedicated engineer and platform, month-to-month, up to 500 user flows; beyond that it says pricing scales pro rata. It also says unlimited runs. Treat these as public offer terms at the checked date; pilot and final contract terms were not investigated. [Pricing FAQ on homepage](https://bug0.com/).

**Confidence / unresolved.** High confidence in current managed positioning and README capabilities; no execution validation. Older Studio positioning appears in search results, but current Studio availability was not independently established. Passmark source-level assertion behavior, model error correlations and reported savings were not audited. The library and managed service should remain separate comparison units.

## Autonoma

**Documented workflow.** The connected-repository product builds PR preview environments, seeds data, executes natural-language tests and reports results on the PR. Its public repo contains Markdown/YAML tests with separate intent and verification fields. The current planner docs describe project/page/data mapping, a knowledge base, scenario design, test generation and validation, with resumable progress and locally inspectable output. The integrated planner can also hand setup/integration work to a coding agent. [Introduction](https://docs.autonoma.app/), [public repository](https://github.com/autonoma-ai/autonoma), [planner](https://docs.autonoma.app/test-planner/).

**Concrete ideas to borrow.**

1. Expose startup discovery as inspectable stages and artifacts: project map, routes, prerequisites, proposed journeys, readiness check. Resume from the unfinished stage. Qabot can provide this within its approval boundary; the output should state what was discovered versus assumed. Autonoma's planner offers a concrete precedent for visible progress and resume. [Planner](https://docs.autonoma.app/test-planner/).
2. Model fixture readiness and cleanup as evidence, not setup trivia. Autonoma's Environment Factory has discover/up/down actions, uses real app creation functions, provides data plus authentication, and tears down only created records. Qabot need not introduce a backend SDK: initially it can document approved existing seed/reset commands and report whether they ran and what remains unverified. [Environment Factory](https://docs.autonoma.app/environment-factory/).
3. Preserve separate journey intent and observable verification. An action such as placing an order is distinct from verifying its presence in order history. This is visible in Autonoma's README test example and maps directly to qabot's actor/judge separation. [Repository test format](https://github.com/autonoma-ai/autonoma).

**Risk / anti-pattern.** The planner docs describe an autonomous integration mode that edits real backend code and pushes a PR, with a permission mode default that bypasses permissions. That is a product-scope mismatch for qabot. Borrow staged transparency, not automatic integration changes. Fixture creation through real functions can still trigger real downstream side effects; a local plan must enumerate the applicable environment/service boundaries. [Planner](https://docs.autonoma.app/test-planner/), [Environment Factory](https://docs.autonoma.app/environment-factory/).

**Confidence / unresolved.** High confidence in retrieved planner/factory docs and repository format; no execution validation. Root docs and homepage occasionally returned fetch errors, while this research lane successfully retrieved the exact planner/factory pages. The coordinating agent's subsequent planner recheck returned HTTP 402, so independent retrieval was not repeatable in this session; the findings retain the successful source retrieval rather than implying a fresh reconfirmation. The repository describes BSL 1.1 and future Apache conversion; do not repeat its marketing phrase 'open source' as an unqualified license classification. No exact current price verified from a dedicated pricing source. No immutable human approval contract established by the reviewed material.

## Highest-Value Adaptations for Qabot

1. **A coverage ledger in the offline report:** criterion -> observed evidence -> result -> uncovered portion -> reason. This makes existing PASS/FAIL/BLOCKED semantics useful to a reviewer instead of treating the labels as differentiation. Inspired most concretely by [Mo reports](https://momentic.ai/docs/mo/reports).
2. **Fresh reproduction for suspected product defects:** retain discovery evidence, rerun from an explicit clean state under a bounded budget, and show whether reproduction succeeded. Keep intermittent/inconclusive observations visible. Inspired by [Mo's separate reproducer](https://momentic.ai/docs/mo).
3. **Inspectable, resumable readiness planning:** show source-derived startup/auth/fixture requirements and validate only approved setup steps; never upgrade missing prerequisites into successful coverage. Inspired by [Autonoma planner](https://docs.autonoma.app/test-planner/) and [Environment Factory](https://docs.autonoma.app/environment-factory/).

These are product recommendations, not implementation instructions or claims that competitors lack qabot's existing controls. A defensible differentiator needs evidence of qabot's complete local, human-approved, version-bound workflow, rather than isolated claims about browser agents, independent contexts, blocked results or screenshots.
